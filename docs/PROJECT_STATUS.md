## 4. 方法开发与初步验证

文档：`research/METHOD.md`

本阶段用于提出、实现和初步验证各个创新点，并将获得支持的创新点逐步集成为完整方法候选。

初步验证用于判断创新点是否值得保留，不替代完整方法稳定后的正式主结果、消融和分析实验。

创新点管理规则：

* 对独立的创新方向使用 `I01`、`I02`……

* 仅当同一创新点经历实质性设计迭代时，才使用 `I01-v1`、`I01-v2`……

* 每个创新点应说明其研究假设、预期作用和初步验证方式。

* 描述和结论应保持简洁；详细动机、方法设计、公式、实现和初步实验应写入 `METHOD.md`。

* 在表中保留已放弃或被取代的创新点，以便持续追溯方法的演进。

推荐状态：

* `Proposed` — 已形成想法，但尚未完成实现或验证

* `Testing` — 正在实现或通过初步实验验证其预期作用

* `Active` — 已获得初步证据支持，并保留在当前完整方法候选中

* `Retired` — 未获得支持、存在明显问题，或已被后续设计取代

## 5. 正式实验与证据计划

文档：`research/EXPERIMENT_PLAN.md`

正式实验以稳定的完整方法候选为对象，用于验证整体效果、各创新点的贡献、方法的稳定性，以及对实验现象的解释。

逻辑顺序为：

`创新点初步验证 → 完整方法集成 → 默认配置确定 → 正式实验 → 证据完整性检查`

其中，完整方法和默认配置确定后，主结果、消融、参数敏感性和分析实验可以根据资源情况并行执行，不要求严格串行。

### 5.1 完整方法与实验协议

* [ ] 完整方法包含哪些 `Active` 创新点，是否已经明确？

* [ ] 正式实验使用的方法版本、默认参数和实验协议是否已经明确？

* [ ] 用于选择默认配置的探索性实验，是否与用于报告结论的正式实验进行了区分？

### 5.2 正式实验证据

* [ ] 主结果实验是否规划完整，能够验证完整方法的整体效果？

* [ ] 每个 `Active` 创新点是否都有对应的消融或对照实验？

* [ ] 必要时，是否规划了创新点之间的交互作用实验？

* [ ] 是否规划了必要的参数敏感性、鲁棒性或适用范围实验？

* [ ] 是否规划了支撑方法解释所需的机制、现象、案例、效率或复杂度分析？

### 5.3 结论与产物检查

* [ ] 每条核心研究结论是否都能对应到具体的 Experiment？

* [ ] 论文需要的关键表格和图，以及对应的实验和数据来源是否已经规划完整？

* [ ] 是否已经检查核心研究结论，确认没有明显缺失或重复的实验证据？
